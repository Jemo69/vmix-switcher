1. Current Bottleneck Breakdown

In the current implementation, the live preview operates as a periodic snapshot fetch using vMix's SnapshotInput API function. While functional, several technical factors constrain performance down to approximately 1 frame every 5 seconds (0.2 FPS):

⚠ Hardcoded Safety Throttle

In vmix/client.py, SNAP_MIN_MONITOR_INTERVAL = 5.0 and SNAP_MIN_INPUT_INTERVAL = 15.0 enforce a minimum 5s/15s pause before asking vMix for new snapshots, regardless of the UI's 1–10 FPS setting.

⚡ Redundant HTTP Polling

In public/js/app.js, the browser runs an interval loop at previewFps (4–10 Hz) requesting every visible thumbnail with &_t=Date.now(), creating 40+ HTTP GET requests/sec over Wi-Fi for static files.

📦 Full Native Resolution Payloads

vMix exports snapshots at full native resolution (1080p or 4K, 1–3 MB per JPEG). Transferring and decoding these huge files on mobile browsers causes micro-stutters and memory churn.

2. The GDI+ Bug & File-Lock Physics

Root Cause of "A generic error occurred in GDI+":
vMix is built on .NET and DirectX. When vMix executes SnapshotInput, it performs Bitmap.Save(path, ImageFormat.Jpeg). If the target file path (e.g. snap_1.jpg) is currently being read by Python (with open(path, "rb") as fh), Windows raises ERROR_SHARING_VIOLATION. In .NET, unhandled sharing violations in GDI+ surface as the dialog popup error.

To stop this error storm, defensive throttling was introduced in v1.3.3. However, the root problem is shared file paths, not request frequency. By isolating the file writes, this restriction can be eliminated entirely.

3. Tier 1: Optimized Snapshot Pipeline (Zero Extra Tools)

This tier requires no third-party media servers or changes to vMix workflows. It optimizes the existing Python/FastAPI backend and frontend:

A. Atomic Temporary Files (Eliminates GDI+ Errors Forever)

Instead of overwriting snap_{key}.jpg, instruct vMix to write to an isolated unique file with a timestamp:

# vMix writes to a unique path that Python is NOT reading:
temp_filename = f"snap_{key}_{int(time.time() * 1000)}.jpg"
temp_path = os.path.join(self._snap_dir_path(), temp_filename)

# Once the HTTP request returns 200, vMix has closed the file:
await self._fetch_url(f"http://127.0.0.1:8088/api/?Function=SnapshotInput&Input={key}&Value={temp_path}")

# Read and cache in memory, then immediately unlink:
with open(temp_path, "rb") as fh:
    raw = fh.read()
os.unlink(temp_path)
self._thumb_cache[key] = (time.time(), raw, "image/jpeg")

Result: Zero file lock collisions. Update frequency for Program & Preview can be safely accelerated from 5s down to 500ms–1000ms (1–2 FPS).

B. Server-Side Downscaling (Pillow)

Downscale full-res captures before serving to clients:

  • Switcher Grid Cards: 320×180 px, JPEG quality 68 (~15–20 KB vs 2 MB).
  • Program / Preview Monitors: 640×360 px, JPEG quality 75 (~40–55 KB).
  • Bandwidth Reduction: Over 95% less Wi-Fi traffic, instantaneous loading on iPhones/iPads.

C. WebSocket Frame Push (Replaces 40 HTTP reqs/sec)

Instead of the client polling blind with setInterval, the backend informs the browser via the existing WebSocket connection when a fresh frame is ready:

// Client WebSocket listener in app.js:
if (data.type === 'thumbnail_ready') {
  const targetImg = document.querySelector(`[data-thumb-input="${data.inputKey}"]`);
  if (targetImg) {
    targetImg.src = `/api/vmix/thumbnail/${data.inputKey}?v=${data.timestamp}`;
  }
}

D. HTTP 304 Not Modified Support

Add ETag or Last-Modified headers in server.py. If a client queries an unchanged frame, return 304 Not Modified with 0 payload bytes.

4. Tier 2: Real-Time Motion via MJPEG Streaming

For operators needing smooth motion on Program and Preview without full WebRTC infrastructure, HTTP Multipart MJPEG provides continuous streaming supported natively by all web browsers.

@app.get("/api/vmix/stream/{channel}.mjpg")
async def mjpeg_stream(channel: str, _: bool = Depends(require_auth)):
    async def frame_generator():
        while True:
            frame_bytes = await vmix_client.get_latest_frame(channel)
            yield (b"--frame\r\n"
                   b"Content-Type: image/jpeg\r\n\r\n" + frame_bytes + b"\r\n")
            await asyncio.sleep(0.1) # 10 FPS

    return StreamingResponse(frame_generator(), media_type="multipart/x-mixed-replace; boundary=frame")

In the browser, this requires no JavaScript polling at all:

<!-- Natively decodes and renders in Safari, Chrome, and Firefox -->
<img src="/api/vmix/stream/program.mjpg" class="monitor-screen-img" alt="Program Stream" />

5. Tier 3: True Broadcast Video via SRT & WebRTC

True 30–60 FPS Broadcast Video: For lip-sync confidence, smooth camera tracking, and director-level switching, stream directly out of vMix's hardware-accelerated video pipeline (NVENC) rather than relying on still snapshots.

vMix SRT Output → WebRTC WHEP Bridge

  1. In vMix: Go to Settings > Outputs / NDI / SRT. Set Output 2 (Preview) or Output 1 (Program) to SRT Caller pointing to srt://127.0.0.1:8890.
  2. Media Relay: Bundle MediaMTX (single lightweight binary, zero configuration). It ingests SRT and exposes WebRTC WHEP.
  3. Browser Playback: Standard HTML5 <video> element connects via WebRTC with < 200ms latency at full 60 FPS 1080p.

8. Recommended Action Plan

To achieve the best outcome with minimum disruption:

  1. Step 1 (Immediate): Implement Tier 1 in vmix/client.py. Switch to timestamped temporary snapshot files. This permanently eliminates GDI+ collisions and allows lowering the Program/Preview refresh interval to 1 second.
  2. Step 2 (Network Optimization): Add server-side thumbnail resizing using Pillow and transition client updates to WebSocket events, slashing Wi-Fi load by over 90%.
  3. Step 3 (High-Fidelity Expansion): For productions demanding fluid 60 FPS video, add optional SRT-to-WebRTC streaming for the main Program and Preview monitors.
